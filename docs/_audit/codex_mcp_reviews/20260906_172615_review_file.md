## Summary

Der Workflow wird nicht allein durch die Öffentlichkeit des Repos für Außenstehende auslösbar: Es gibt keinen PR-Trigger, und `workflow_dispatch` erfordert Schreibzugriff. Zwei sicherheitsrelevante Schwächen bleiben jedoch: Deploy-Rechte gelten unnötig bereits im Build-Job, und manuelle Deployments sind nicht sichtbar auf `main` beschränkt.

## Blockers

- **Deploy-Berechtigungen sind auf Workflow-Ebene vergeben.** Dadurch erbt der `build`-Job in `.github/workflows/docs.yml` ebenfalls `pages: write` und `id-token: write`, obwohl nur `deploy` diese Rechte benötigt. Gerade `npm ci` und `npm run build` führen Code aus dem öffentlichen Repository und aus 1399 Abhängigkeiten aus. Beschränken auf:

  - Build-Job: höchstens `contents: read`
  - Deploy-Job: `pages: write` und `id-token: write`; `contents: read` nur falls tatsächlich benötigt

  GitHub unterstützt jobweise Berechtigungen und setzt nicht genannte Scopes auf `none`. Das entspricht auch dem aktuellen offiziellen Pages-Beispiel, das die Schreibrechte am Deploy-Job zeigt. [Workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [GitHub Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

- **`workflow_dispatch` kann von Schreibberechtigten mit einem frei gewählten Branch/Ref gestartet werden.** Ein Benutzer mit Write-Zugriff kann damit einen eigenen Branch samt verändertem `website/**`, Lockfile oder Workflow deployen, ohne dass dieser Stand zuvor nach `main` gelangt. Außenstehende ohne Write-Zugriff können das nicht; GitHub verlangt Write-Zugriff für manuelle Runs. Das sollte durch eine der folgenden Maßnahmen geschlossen werden:

  - Deployment nur zulassen, wenn `github.ref == 'refs/heads/main'`, oder
  - im `github-pages`-Environment ausschließlich `main` als Deployment-Branch erlauben, idealerweise zusätzlich mit Required Reviewers.

  [GitHub: Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow?tool=webui)

## Suggestions

- Die vier Actions sind mit beweglichen Major-Tags statt vollständigen Commit-SHAs referenziert. Das ist ein reales, wenn auch bei offiziellen `actions/*`-Repositories relativ kleines Supply-Chain-Risiko: Ein kompromittierter Action-Account oder bewegter Tag könnte Code mit den Job-Rechten ausführen. Für die wichtigste Produktdomain sollten die Actions auf verifizierte vollständige SHAs gepinnt und automatisiert aktualisiert werden. GitHub bezeichnet vollständige SHAs als einzige unveränderliche Referenz. [GitHub secure use reference](https://docs.github.com/en/actions/reference/security/secure-use?learn=getting_started)

- Für beide Jobs sollten `timeout-minutes` gesetzt werden, beispielsweise großzügig für den Build und kurz für den Deploy. Das begrenzt Hänger und absichtlich ressourcenintensive Install-/Build-Skripte.

- `npm ci` führt Lifecycle-Skripte aus. Ein kompromittiertes Paket braucht keine Pages-Credentials, um die ausgelieferte Seite zu verändern: Es kann während Installation oder Build den Inhalt von `website/build` manipulieren; genau dieses Artefakt wird anschließend vertrauensvoll deployt. Es gibt dagegen keinen erkennbaren Weg, wie das Artefakt selbst Code im separaten Deploy-Runner ausführt. Prüfen, ob `npm ci --ignore-scripts` mit dem Projekt funktioniert; andernfalls Lockfile-Änderungen besonders schützen und Dependency-Updates kontrolliert prüfen.

- `push` auf `main` ist korrekt auf `website/**` und den Workflow begrenzt. Ein fremder Pull Request startet diesen Workflow nicht. Erst wenn dessen Änderung gemergt oder anderweitig nach `main` gepusht wird, erfolgt der Deploy. Forks führen gegebenenfalls ihre eigene Kopie im Fork aus, nicht den Upstream-Deploy.

- `cancel-in-progress: false` verhindert Parallelität, lässt aber veraltete Deployments vor dem neuesten Stand ablaufen. Das ist sicherheitsneutral, kann jedoch kurzfristig ältere Inhalte ausliefern. Für Webseiten ist `true` häufig sinnvoller, sofern ein abgebrochener Deploy zuverlässig wiederholt werden kann.

## Notes

- `contents: read`, `pages: write` und `id-token: write` sind grundsätzlich die passenden Pages-Berechtigungen; die Öffentlichkeit des Repos erweitert diese Tokenrechte nicht auf beliebige Besucher. Das Problem ist ihre derzeit zu breite Vererbung an den Build-Job.
- `contents: read` ist für ein öffentliches Repository zwar wenig sensibel, für `checkout` aber normal und angemessen.
- Das deklarierte `environment: github-pages` allein erzwingt keine Freigabe oder Branch-Beschränkung. Solche Regeln müssen in den Repository-Einstellungen konfiguriert sein.
