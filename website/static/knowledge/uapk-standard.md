## Frequently Asked Questions

**Q: Can I use the UAPK Gateway node with n8n Cloud, or only self-hosted?**
A: The `n8n-nodes-uapk-gateway` package is a community node. As of March 2026, n8n Cloud supports community nodes, so you can install it on both cloud and self-hosted instances. Check n8n's community node documentation for the latest compatibility details.

**Q: How does the triple output differ from using a Switch node after a regular HTTP request?**
A: The triple output is evaluated server-side by the UAPK Gateway and routed natively by the node. This means the workflow topology itself reflects the governance logic — you can see at a glance which branch handles allowed, denied, and escalated actions. With a Switch node, you would need to parse the HTTP response, handle edge cases, and manually route. The UAPK node handles all of this internally, including error states and timeout fallbacks.

**Q: What happens if the UAPK Gateway is unreachable during workflow execution?**
A: The node follows a fail-closed policy by default — if the Gateway cannot be reached, the action is denied. This ensures that network issues never result in ungoverned actions. You can configure a timeout (default: 10 seconds) and a fallback decision in the node settings. For mission-critical workflows, we recommend deploying the UAPK Gateway in the same network or region as your n8n instance.

**Q: Does the node support batch evaluation for workflows that process multiple items?**
A: Yes. When n8n passes multiple items to the UAPK Gateway node, each item is evaluated individually against the policy set. The triple output routes each item independently, so in a batch of 100 items, 95 might be allowed, 3 denied, and 2 escalated — each routed to the appropriate downstream branch.

**Q: Can I use different policies for different n8n workflows?**
A: Absolutely. The Evaluate and Execute operations accept a `policy_set` parameter. You can configure different policy sets in your UAPK Gateway dashboard and reference them by name in each n8n workflow. This allows a customer-support workflow to use lenient policies while a financial-operations workflow uses strict ones.
